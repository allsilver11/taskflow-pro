## 읽는 순서

```
00-overview  →  01-product  →  02-specs  →  03-design  →  04-tasks  →  05-conventions
   (지도)          (목적)         (재료)        (설계도)      (일정)          (규칙)
```

작업을 시작하기 전에 반드시 위 순서대로 읽는다.
앞 문서를 건너뛰면 뒤 문서의 결정 근거를 파악할 수 없다.

---

## 왜 이렇게 나누는가 — 관심사 분리 원칙

소프트웨어 설계에서 관심사 분리(Separation of Concerns)란 **"서로 다른 이유로 변경되는 것은 서로 다른 곳에 둔다"** 는 원칙이다.
문서도 같은 원칙이 적용된다.

| 관심사 | 변경 이유 | 담당 문서 |
|--------|-----------|-----------|
| 제품 방향 | 비즈니스 목표·사용자 요구가 바뀔 때 | `01-product.md` |
| 기술 선택 | 스택 교체·API 변경이 생길 때 | `02-specs.md` |
| 구조 결정 | 아키텍처 리팩토링이 필요할 때 | `03-design.md` |
| 작업 현황 | 스프린트가 진행되며 매일 바뀔 때 | `04-tasks.md` |
| 협업 규칙 | 팀 규모·프로세스가 바뀔 때 | `05-conventions.md` |

**한 곳에 모두 쓰면 생기는 문제:**
- "API 스펙을 바꿨는데 어디를 고쳐야 하지?" → 전체 문서를 뒤진다.
- 제품 기획자가 기술 명세 문서를 열어 필요한 정보를 찾지 못한다.
- 커밋 메시지가 "문서 수정"으로 뭉뚱그려져 변경 이력을 추적할 수 없다.

**나눠두면 얻는 것:**
- 각 문서의 **독자가 명확**해진다 (기획 vs 개발 vs 운영).
- 변경이 생겼을 때 **영향 범위를 정확히 알 수 있다**.
- Claude가 작업 전에 **필요한 맥락만 골라 읽을 수 있다**.
